# Configuration

Settings are layered in two files under the base directory:

- **Reference file** (`config.yaml`): generated, lists every field with its default, and is regenerated by setup. Never edited by hand.
- **Override file** (`config-override.yaml`): the user's own settings. Only fields present here replace defaults.

The effective configuration is defaults plus overrides. `tacit config view` shows it, tagging each field as default or overridden.

## Why two files

Defaults change between releases. If users edited one shared file, an upgrade would either clobber their changes or leave them on stale defaults. Keeping the user's choices in a separate file lets defaults move freely.

## Edits preserve the file

Setting or clearing a field edits the override file in place, keeping comments and unrelated lines. A value that would leave the file unloadable is refused with nothing written. Keys that no longer exist are ignored rather than rejected, so removing a feature does not break old override files.

## Setup shares one code path

`tacit setup` (terminal) and the app's onboarding window both go through the same setup logic: validate choices, check the classifier is reachable, write the files. The window and the wizard cannot drift apart. The app's settings window uses the same field editing as `tacit config set`.

## Groups

Settings fall into transcription (model, language, hallucination controls), segmentation (timings and thresholds, see [segmentation](segmentation.md)), and classification (provider, model, which agent the skills install for). The per-field reference is in the README.

## Changes need a restart

The daemon reads configuration once at start. The app offers a restart after a change.
